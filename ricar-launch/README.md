### Описание
Репозиторий для запуска автопилота

### Установка
```shell
sudo pip install ricar_launch/.
sudo activate-global-python-argcomplete3
```

### Конфигурация

| Файл                        | Описание                                                                        |
|-----------------------------|---------------------------------------------------------------------------------|
| common.yaml                 | Базовые сервисы для распределения ресурсов                                      |
| init-compose.yaml           | Сервисы, отвечающие за запуск основных (обязательных) сервисов для работы стека |
| docker-compose.yaml         | Сервисы, отвечающие за запуск конкретного компонента стека                      |
| .env                        | Хранит переменные для common.yaml, docker-compose.yaml                          |
| launch.yaml                 | Верхний уровень абстракции с конфигурацией для запуска стека быстрыми командами |
| predefined_tasks.yaml       | Предопределенные команды для исполнения внутри сервисов                         |

Конфигурация использует единый `CYCLONEDDS_URI` из файла `.env` для всех сервисов.

### Файл .env

Переменные из `.env` читаются `docker compose` при каждом вызове `ricar` и подставляются в `common.yaml` и `docker-compose.yaml`. Менять `.env` нужно до запуска: значения фиксируются в момент создания контейнера, уже запущенный контейнер их не перечитывает.

| Переменная             | Влияние                                                                                                                                              |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| `IMAGE`                | Образ, из которого создаются все контейнеры стека (и init-сервисы). Главный переключатель того, какой билд запускается.                               |
| `CMD`                  | Шелл-обертка, в которой стартует команда сервиса (по умолчанию `/bin/bash -ic`.                                    |
| `LOGGING_MODE`         | Режим логирования: `debug` / `auto` / `manual`. Определяетрежим логирования.                                                   |
| `EXPERIMENT_GROUP_NAME`| Имя группы экспериментов. Если пусто — `LOGGING_DIRECTORY` становится `default`. Используется в режиме `manual`.                                       |
| `LOGGING_DIRECTORY`    | Имя группы логов в режиме `manual`. Вычисляется как `${EXPERIMENT_GROUP_NAME:-default}`.                                                              |

Логирование дополнительно требует переменную окружения `VEHICLE_ID` (наследуется в контейнер из окружения хоста). Без нее сервис логирования не запустится.

### Режимы логирования

Профиль `logging` пишет логи в `/logs/<группа>/<временная_метка>/`. Имя группы выбирается по `LOGGING_MODE`, `LOGGING_DIRECTORY` и `VEHICLE_ID`:

| `LOGGING_MODE`           | Директория группы           | Когда использовать                                                                 |
|--------------------------|-----------------------------|------------------------------------------------------------------------------------|
| `debug`                  | `debug_<VEHICLE_ID>_<ts>`   | Отладка. Также используется как fallback, если `LOGGING_DIRECTORY` пуст.            |
| `auto`                   | `auto_<VEHICLE_ID>_<ts>`    | Штатные заезды для расчета метрик.                                                      |
| `manual`                 | `<LOGGING_DIRECTORY>` | Группировка по имени эксперимента `EXPERIMENT_GROUP_NAME` для конкретных тестов.           |

где `<ts>` — временная метка старта (`YYYY_MM_DD_HH_MM_SS_ffffff`).

Внутри директории группы оказываются:
- `*.parquet` — данные топиков (по файлам на топик);
- `params_<ts>.yaml` — снапшот параметров нод;
- `rosbags/<rosbags>` — записи rosbag, сделанные через `ricar start_record`.

> `VEHICLE_ID` обязателен (определен по умолчанию в `~/.bashrc`) — без него запуск логирования падает. Пустой `LOGGING_DIRECTORY` уводит логи в `debug_*`-директорию независимо от режима (по умолчанию он вычисляется из `EXPERIMENT_GROUP_NAME`, а при пустом значении становится `default`).

### Init-сервисы

Перед любым профилем `ricar up` сначала поднимает обязательные init-сервисы из `init-compose.yaml`. Их нельзя перезапускать без полного перезапуска стека.

| Сервис       | Роль                                                                                                                                  |
|--------------|---------------------------------------------------------------------------------------------------------------------------------------|
| `ros-daemon` | Перезапускает `ros2 daemon` и держит его живым. Готовность проверяется healthcheck-ом (ищет процесс `_ros2_daemon`).                  |
| `cleanup-logging` | Удаляет логи старше 7 дней.                                                                                                      |
| `wait-init`  | Барьер для поднятия остальных сервисов: через `depends_on` ждет, пока `ros-daemon` не станет healthy, а `cleanup-logging` не завершится, и только после этого стек поднимает все прочие профили. Гарантирует, что остальные сервисы стартуют на уже готовом ROS-демоне. |

Init-сервисы `ros-daemon` и `wait-init` поднимаются один раз и продолжают работать даже после `ricar down` профиля. Init-сервис `cleanup-logging` останавливается после выполнения очистки. Команды `ricar down` / `ricar restart` не влияют на Init-сервисы — остановить их можно только отдельными debug-командами (`terminate-init`, `terminate-all`).

### Запуск и остановка системы
Осуществляется через профили. Все профили можно посмотреть в compose/docker-compose.yaml<br/>

Запуск контейнеров (поднимает те контейнеры, которые не запущены; если контейнера нет — создает его. Уже существующие контейнеры не пересоздаются и не перечитывают `.env`/образ)
```shell
ricar up all
```

Остановка (убивает контейнеры через SIGKILL, но не удаляет их. Контейнер остается в состоянии Exited, при следующем `up` поднимается тот же контейнер, его содержимое сохраняется)
```shell
ricar down all 
```

### Просмотр доступных команд
Можно посмотреть в launch.yaml или в help:
```shell
ricar -h
```

### Просмотр всех профилей для запуска
Можно посмотреть в compose/docker-compose.yaml или просто запустить команду:
```shell
ricar up
```
* Так можно запускать любую команду, чтобы посмотреть, какие параметры она принимает
* Или воспользоваться автодополнением, т.е. нажать tab 2 раза

### Запуск/остановка всего стека
`up` поднимает отсутствующие контейнеры (существующие не пересоздаются и не перечитывают `.env`/образ), `down` убивает контейнеры через SIGKILL, но не удаляет их — содержимое сохраняется до следующего `up`.
```shell
ricar up all
ricar down all
```

### Запуск/остановка конкретного профиля
То же, что и для всего стека, но в рамках одного профиля: `up` создает/поднимает контейнеры профиля (существующие не пересоздаются), `down` убивает их без удаления.
```shell
ricar up localization
ricar down localization
```

### Перезапуск конкретного профиля
Убивает контейнеры профиля и поднимает их заново. Контейнер не удаляется и не пересоздается (`--no-recreate`) — перезапускается тот же контейнер на прежнем образе, изменения `.env`/образа не подхватываются.
```shell
ricar restart sensing
ricar restart perception
```

### Удалить конкретный профиль (содержимое контейнера не сохранится)
Останавливает и удаляет контейнеры профиля. После этого следующий `up` создаст их заново — уже с актуальными `.env` и образом.
```shell
ricar clean sensing
ricar clean perception
```

### Закоммитить профиль
Сохраняет текущее состояние контейнера сервиса в образ. Сам контейнер не удаляется и не перезапускается. Имя образа может быть как существующим (будет перезаписан тег), так и новым.
```shell
ricar commit logging tvp_image:alpha
ricar commit logging tvp_image:new_tag
ricar commit logging new_image:new_tag
```

### Выполенение команды внутри сервиса
```shell
ricar exec perception ros2 node list
```


```shell

```

### Профили

Профиль объединяет один или несколько сервисов. Полный актуальный список — в `docker-compose.yaml`.

| Профиль             | Что поднимает                                                                                        |
|---------------------|------------------------------------------------------------------------------------------------------|
| `all`               | Весь стек                                                                                            |
| `vehicle`           | Драйверы телеги                                                                                      |
| `map`               | Карты                                                                                                |
| `sensing`           | Обработка данных с сенсоров                                                                          |
| `localization`      | Локализация                                                                                          |
| `perception`        | Восприятие                                                                                           |
| `planning`          | Планирование                                                                                         |
| `control`           | Управление                                                                                           |
| `api`               | API автопилота                                                                                       |
| `tools`             | Вспомогательные инструменты (в т.ч. Foxglove)                                                        |
| `transforms`        | Публикация трансформов                                                                               |
| `visualization`     | Визуализация (в `all` не входит, поднимается отдельно)                                               |
| `logging`           | Логирование топиков в Parquet, снапшот параметров и запись rosbag                                    |
| `logging_benchmark` | Логирование с whitelist'ами для бенчмарка и автоматическим снапшотом параметров                      |
| `benchmark`         | Набор сервисов для бенчмарка + `benchmark_container`                                                 |
| `debug`             | Отладочный контейнер (`sleep infinity`) — для ручной работы внутри образа                            |

## Troubleshooting

### Контейнер падает из-за ошибки в коде

Симптом: после `ricar up <профиль>` сервис не работает, в `ricar ps` он в состоянии `Exited`, а `ricar logs <профиль>` показывает трейсбек/ошибку сборки.

Чинить прямо в упавшем контейнере неудобно (он перезапускается/падает). Поэтому правим код в отдельном debug-контейнере, коммитим образ и перезапускаем упавший сервис на новом образе.

1. Поднять отладочный контейнер (он просто «спит» и не падает):
   ```shell
   ricar up debug
   ```

2. Зайти внутрь и исправить код:
   ```shell
   ricar enter debug
   # внутри контейнера: правим исходники, при необходимости пересобираем
   #   colcon build --packages-select <пакет>
   # проверяем, что ошибка ушла
   ```

3. Закоммитить состояние debug-контейнера в образ, из которого запускается стек (имя образа — из `.env`, переменная `IMAGE`):
   ```shell
   ricar commit debug tvp_image:alpha
   ```
   `ricar commit` берет имя сервиса (`debug`), сам находит его контейнер и коммитит в указанный образ. Имя образа можно указать как существующее, так и новое.

4. Перезапустить упавший сервис — он создастся заново уже из обновленного образа:
   ```shell
   ricar clean <профиль>   # удалить старый контейнер, чтобы подхватился новый образ
   ricar up <профиль>
   ```
   `clean` нужен потому, что `restart` не пересоздает контейнер (`--no-recreate`) и продолжит работать на старом образе.
